## 3. Project Overview

### 3.1 Purpose and Users

TradeHub (see `app/layout.tsx`'s `SITE_NAME` and `SITE_DESCRIPTION`) is a wholesale/B2B-style marketplace: *"TradeHub connects buyers with verified suppliers across automobiles, tech, home, tools, and more — browse, compare, and order in bulk with confidence."* The product model (`types/product.ts`) supports quantity price tiers (`PriceTier`), supplier verification (`verified: boolean`), and bulk-order framing ("Request a Quote" rather than a simple "Buy Now"), which distinguishes this from a plain consumer storefront.

### 3.3 Architecture

**Framework.** Next.js 16 App Router with Turbopack (the default dev/build engine for this Next.js version), React 19, TypeScript in `strict` mode.

**Rendering strategy.** The project deliberately keeps data-heavy, crawlable pages as **Server Components** with plain functions doing the work (`services/productService.ts` has no `"use client"` and no DOM/React dependency, so it runs identically on the server or the client). `app/listing/page.tsx` is a clear example: filtering, sorting, and pagination all happen server-side from `searchParams`, so the resulting HTML is fully formed on first load with zero client-side JavaScript required to see filtered results — verified by inspecting the file's own comment: *"This page reads `searchParams` ..., which makes Next.js render it dynamically per request... SSR ... is right here, while the Home and Product pages use ISR."*

**Client state.** Interactive, per-visitor state (cart, wishlist, currency, auth, the AI panel) lives in React Context providers, all composed in `app/layout.tsx`:

```
AuthProvider
  AuthModalProvider
    ConfirmDialogProvider
      CartProvider
        WishlistProvider
          ShipCountryProvider
            CurrencyProvider
              AIAssistantProvider
                Navbar / <main> / Footer / AIAssistantPanel
```

This nesting order is taken directly from `app/layout.tsx`.

**Data layer.** There is no external database or backend API for product data. `services/productData.ts` contains a static, hand-authored catalog (verified: **59 products** across **9 categories** and **43 distinct brands** — counted directly from the file). `services/productService.ts` is the single, pure-function data-access layer over that catalog (filtering, sorting, pagination, recommendations, supplier assignment, price tiers, review generation). Every feature in the app — the listing page, the AI Assistant's tool call, the navbar search suggestions, the auth page's showcase carousel — calls through this same module rather than each maintaining its own copy of catalog logic.

**Authentication.** There is no real backend or session system. `context/AuthContext.tsx`'s own comment states this directly: *"This project deliberately has no auth backend... signing in here just records a name/email locally."* `hooks/useAuthForm.ts` implements a local "account book" in `localStorage` (`auth-accounts` key) so that "invalid email or password" is a real, checkable condition rather than an unconditional success — see Section 4 for the reasoning captured in that file.

**Cart/Wishlist/Orders.** All three follow the same pattern: React state hydrated from `localStorage` in a `useEffect` on mount (never during render, to avoid an SSR/CSR markup mismatch), then written back to `localStorage` on every change. `services/orderService.ts` scopes saved orders to the signed-in user's own email (`orders:${email}`) and explicitly does not attempt to persist guest orders — its own comment states the reasoning: a guest has no account to later look the order up under, so the checkout confirmation says so honestly rather than pretending an order was saved.

**Messaging/Profile.** `/messages` implements a buyer-facing inquiry UI that can be pre-filled with a specific product reference when reached via a product's "Send inquiry" action (confirmed by `MessageProductRef` handling in `app/messages/page.tsx`, per the project's own history — this specific wiring is also referenced in the conversation record, see Section 15). `/profile` aggregates account info, saved addresses, and order history (via `orderService.getOrders`).

**Responsive behavior.** The project does not use a component library or a utility-CSS framework — every visual layer is a CSS Module (`*.module.css`) using a shared token set (`app/globals.css`: color, spacing, radius, and typography custom properties). Two breakpoint conventions are used consistently across the codebase: `56rem` for header/navigation collapse (`components/Navbar.module.css`, `components/MobileNavDrawer.module.css`) and `64rem` for the auth pages' side-by-side/stacked layout switch (`components/AuthSplitPage.module.css`).

**Accessibility considerations.** See Section 10 for full detail. In summary: a skip-link, a global focus-visible ring, an `.sr-only` utility, `prefers-reduced-motion` handling, and a 44px minimum interactive-target rule are all defined once in `app/globals.css` and used throughout rather than being re-implemented per component.

**Performance considerations.** See Section 9. In summary: ISR on catalog-driven pages, `next/image` throughout with explicit `sizes` on `fill`-mode images, lazy-loading on below-the-fold product images, and a context-splitting pattern in the AI Assistant specifically to avoid re-rendering the whole app on every streamed token.

## 4. Engineering Decision Record

### Decision: Mock authentication with a local, checkable "account book"

**Problem/Requirement**
The project needs sign-in/sign-up behavior for account-gated features (wishlist, checkout, reviews) without a real backend.

**Options/Considerations**
(a) No validation at all — any email/password combination "succeeds." (b) A real backend with hashed credentials. (c) A local, in-browser record of created accounts that sign-in validates against.

**Chosen Approach**
Option (c). `hooks/useAuthForm.ts` stores `{ name, password }` per email in `localStorage` under `auth-accounts`. `mode: "create-account"` writes a new entry (and rejects an email that already exists); `mode: "sign-in"` only ever *reads* — it never silently registers an unseen email.

**Reasoning**
The file's own comment states the earlier behavior directly: *"An earlier version of this let Sign In silently register a new account for any never-seen email — that's deliberately gone: Sign In authenticates against an existing local 'account,' it doesn't create one."* This is **verified from the code**, not an interpretation — it documents an actual behavior change.

**Trade-offs**
Real validation logic (empty-field checks, email shape, minimum password length, duplicate-account detection) without the cost/scope of a real backend — but the "account" is only ever local to one browser and is explicitly labeled a prototype in the UI (`AuthSplitPage.tsx`'s "Prototype." notice).

**AI Contribution**
Implementing the validation branches and the `localStorage`-backed account map is the kind of boilerplate AI assistance is well suited to generating quickly once the *rule* (sign-in reads, create-account writes) is specified.

**Human Judgment**
The security-relevant decision — that a failed sign-in returns the *same* generic message ("Invalid email or password.") whether the email doesn't exist or the password is wrong — is a deliberate choice to avoid email enumeration, documented directly in the file's comment. Choosing that behavior, and choosing to disclose it as a prototype rather than implying real account security, is a judgment call about what a demo should and shouldn't claim.

### Decision: `localStorage` hydration via `useEffect`, not lazy `useState` initializer

**Problem/Requirement**
Cart, wishlist, auth, and search-history state needs to persist across page loads, but Next.js Server Components render on the server first, where `localStorage` does not exist.

**Options/Considerations**
(a) Read `localStorage` directly in a lazy `useState(() => ...)` initializer. (b) Read it in a `useEffect` after mount, with a `hydrated` flag gating the corresponding "save" effect.

**Chosen Approach**
Option (b), identically in `context/CartContext.tsx`, `context/AuthContext.tsx`, and `context/WishlistContext.tsx`.

**Reasoning**
Option (a) would run during the render Next.js uses to produce server-rendered HTML, where `window.localStorage` throws or is undefined, or would otherwise produce a hydration mismatch between server-rendered markup and the client's first paint. The `useEffect` pattern only runs after the client has mounted, avoiding that mismatch — this reasoning is visible directly in `CartContext.tsx`'s own comment: *"Load from localStorage once on mount (client only — avoids hydration mismatch between server-rendered HTML and browser state)."*

**Trade-offs**
The UI briefly renders an "empty" cart/wishlist/auth state before the effect runs (usually imperceptible), in exchange for correctness across server/client rendering. The `hydrated` flag additionally prevents the *save* effect from firing with an empty array before the *load* effect has had a chance to run, which would otherwise silently wipe out a returning visitor's saved cart on every reload — a real bug this pattern specifically avoids.

**AI Contribution**
This exact pattern recurs across four different context files with the same structure — evidence that it was applied consistently once established, which is a pattern AI assistance can help replicate correctly across multiple files without copy/paste drift.

**Human Judgment**
Every instance of this pattern also carries a project-specific ESLint suppression comment (`// eslint-disable-next-line react-hooks/set-state-in-effect`) with a justification, rather than a blanket rule disable — see Section 7's dedicated issue on this rule for the debugging history behind it. Recognizing *when* this lint rule is a real problem versus a legitimate external-store sync is a judgment call, not something that can be applied mechanically.

### Decision: Native `<dialog>` element for every modal surface

**Problem/Requirement**
The app needs several modal dialogs (product-detail request dialogs, the mobile filter drawer, the mobile navigation drawer, the auth quick-modal) with focus trapping, Escape-to-close, and an inert background.

**Options/Considerations**
(a) Hand-roll a modal with `position: fixed`, manual focus trapping, and manual `aria-*` wiring. (b) Add a third-party dialog/modal library dependency. (c) Use the native HTML `<dialog>` element and its `showModal()` API.

**Chosen Approach**
Option (c) — `components/Dialog.tsx`, `components/MobileFilterDrawer.tsx`, and `components/MobileNavDrawer.tsx` all wrap a real `<dialog>` element.

**Reasoning**
`Dialog.tsx`'s own comment: *"showModal() gives a real focus trap, Escape-to-close, an inert background page, and focus moving into the dialog, all for free from the browser — no ARIA framework to hand-roll, no dependency to add."* This avoids both the maintenance burden of option (a) and the dependency weight of option (b) for a browser feature that already does most of the work.

**Trade-offs**
Native `<dialog>` is well supported in current browsers but is not infinitely flexible, and — as documented in Section 7 — its behavior isn't 100% consistent across engines (Tab-order wrapping specifically required a manual fix). It also required deliberately styling around the default `dialog:not([open]) { display: none }` user-agent rule, which several component comments call out explicitly (e.g. `MobileNavDrawer.module.css`: *"display MUST be scoped to `[open]`, not set on the bare `.dialog` class... an unconditional `display` here would keep the dialog visible... even while closed"*).

**AI Contribution**
Generating the repeated boilerplate (ref wiring, `showModal()`/`close()` effect, backdrop-click detection via `e.target === dialogRef.current`) consistently across three separate components.

**Human Judgment**
The AI Assistant panel (`components/AIAssistantPanel.tsx`) is the one place this pattern was *deliberately not reused* — the panel needs to stay open while the rest of the page remains scrollable and interactive, which a modal `<dialog>` cannot do (its whole purpose is to make the background inert). Recognizing that a previously-successful pattern does not fit a new requirement, and choosing a different implementation (`position: fixed` + `inert` toggling) instead of forcing the existing pattern to fit, is a clear design-judgment decision.

### Decision: AI Shopping Assistant built on raw `fetch()`, not a provider SDK

**Problem/Requirement**
Add a real, streaming AI chat assistant that can search the actual product catalog, without introducing unnecessary dependencies.

**Options/Considerations**
(a) The Vercel AI SDK (`ai` package) with a provider adapter. (b) The provider's own SDK (`@anthropic-ai/sdk`, or an OpenAI-compatible client). (c) A raw `fetch()` call against the provider's documented HTTP/SSE endpoint, with a hand-written SSE parser.

**Chosen Approach**
Option (c). `app/api/assistant/route.ts` calls `fetch()` directly and parses the Server-Sent Events stream itself; `lib/ai.ts` holds only configuration (model id, system prompt, tool schema) and no HTTP logic beyond the URL constant.

**Reasoning**
`lib/ai.ts`'s own comment: *"Deliberately no `openai` SDK dependency either: same reasoning as before — one documented HTTP+SSE endpoint, a raw fetch() is less surface area than a full SDK for one streaming call with one tool."* `package.json` confirms only `react-markdown` was added as a new dependency for this entire feature — no AI SDK of any kind is present in `dependencies`.

**Trade-offs**
More code to write and maintain (a full manual SSE event parser and a manual tool-use loop, both in `route.ts`) in exchange for zero new runtime dependencies and full control over the exact wire format sent to the browser. This trade-off is directly visible in `route.ts`'s length and its own comment describing a **custom, minimal SSE protocol to the browser** (`{"type":"text"|"products"|"done"|"error"}`) that is intentionally *not* the Vercel AI SDK's own wire format, because that SDK isn't a dependency here.

**AI Contribution**
Implementing an SSE parser for an OpenAI-compatible chat-completions stream (accumulating `content_block`/`delta` events, handling partial JSON for tool-call arguments) is exactly the kind of well-documented-but-fiddly protocol code AI assistance can produce quickly and correctly once the target wire format is known.

**Human Judgment**
The provider itself was **changed mid-project** — the assistant was originally implemented against the Anthropic Messages API directly, then migrated to OpenRouter specifically to guarantee the project never incurs API cost (see the dedicated decision below). That migration required re-reading and adapting the entire SSE parser (different event names, different tool-call delta shape) rather than a drop-in swap, which is direct evidence of engineering work beyond "ask AI to add an AI feature."

### Decision: Switching the AI provider from Anthropic directly to OpenRouter's free tier

**Problem/Requirement**
The developer explicitly required that the project **never incur any AI API cost** — no Anthropic credits, no OpenAI paid API, no requirement to add a credit card.

**Options/Considerations**
(a) Keep calling the Anthropic API directly and require the developer to supply a paid key. (b) Switch to OpenRouter and pin one specific free (`:free`-suffixed) model. (c) Switch to OpenRouter's own `openrouter/free` router, which selects among currently-live free models automatically.

**Chosen Approach**
Option (c). `lib/ai.ts`: `export const OPENROUTER_MODEL = process.env.OPENROUTER_MODEL || "openrouter/free";`

**Reasoning**
A specific free model was rejected in favor of the router because individually-pinned free models on OpenRouter are known to be added, repriced, or removed on a rolling basis — pinning one risks the feature silently breaking when that model disappears. This reasoning is recorded directly in `lib/ai.ts`'s comment: *"individual free models get added/pulled/repriced from week to week, while `openrouter/free` itself stays a stable, always-free entry point."* This was verified during development by fetching OpenRouter's live public model catalog (`GET https://openrouter.ai/api/v1/models`) and confirming `openrouter/free` supports `tools` and `tool_choice` (required for the catalog-search feature) at $0 price for both prompt and completion tokens.

**Trade-offs**
The router selects a model at random from the free pool rather than a fixed one, so response quality/behavior can vary between requests — an explicit, disclosed limitation rather than a hidden one.

**AI Contribution**
AI assistance was used to fetch and interpret the live OpenRouter model catalog, identify which entries were genuinely free (`pricing.prompt === "0"` and `pricing.completion === "0"`), and confirm tool-calling support before writing any code.

**Human Judgment / Hard Safety Requirement**
The developer's constraint — "no paid fallback, ever, even automatically" — was implemented as a hard runtime guard, not just a default value: `lib/ai.ts` exports `isFreeModelId()`, and `route.ts` calls it on **every request** (not just at startup) before contacting the API, refusing with a clear error (`NON_FREE_MODEL_ERROR`) if `OPENROUTER_MODEL` is ever misconfigured to a non-free id. This is a case where a stated business/cost constraint was translated into an enforced code invariant rather than a comment or a README note — a decision that required understanding *why* a silent fallback would be unacceptable, not just implementing the happy path.

### Decision: Token-based (not whole-string) product search matching

**Problem/Requirement**
The navbar search placeholder promises "Search products, brands and more..." A shopper typing a brand and a product together (e.g. "Lenovo laptop") got zero results even though a matching product existed.

**Options/Considerations**
(a) Keep the original whole-string substring check (`name.includes(q) || desc.includes(q) || brand.includes(q)`). (b) Split the query into words and require every word to appear somewhere in a combined name+description+brand string.

**Chosen Approach**
Option (b), in `services/productService.ts`'s `filterProducts()`.

**Reasoning**
Under the original rule, a query like "Lenovo laptop" is not a substring of the brand field ("Lenovo") alone, nor of the name field ("Laptops") alone — no single field contains the whole two-word phrase. The token-based rewrite concatenates `${name} ${desc} ${brand}` into one haystack and checks that every query word appears **somewhere** in it, so words can each match a different field. This was diagnosed by direct testing: `curl`-equivalent listing-page queries for `Apple` (single brand word, worked), `Lenovo laptop` (brand+product, failed under the old rule), and `Apple watch` (brand+product that does exist together, needed to work) were run against the live app before and after the change to confirm the fix and confirm it didn't introduce false positives.

**Trade-offs**
Token matching is more permissive — it can match a product whose name, description, and brand collectively contain all the query words even if they were never meant to be read together, though for a catalog this size that risk was judged acceptable against the much more common false-negative it fixes.

**AI Contribution**
Proposing the token-splitting rewrite once the root cause (a whole-phrase substring check) was identified.

**Human Judgment**
The root cause itself was found by direct, repeatable testing against the real catalog data (confirming, for instance, that this catalog's one "Apple" product is a smartwatch, not a laptop, so a query like "Apple laptop" *correctly* still returns zero results after the fix — that specific negative case was verified, not assumed) rather than by guessing at a fix and hoping it worked.

### Decision: Disabling (not hiding) unavailable brand filters

**Problem/Requirement**
Once brand filtering was added to `FilterSidebar`, picking a category and a brand that don't intersect (e.g. "Apple" — a Computer & Tech brand — while "Automobiles" is selected) leads to a guaranteed zero-result page.

**Options/Considerations**
(a) Do nothing — let the shopper click into a dead end and find out from the empty-state message. (b) Hide brands that don't apply to the active category. (c) Show every brand always, but render the inapplicable ones as non-interactive (disabled) rather than removing them.

**Chosen Approach**
Option (c). `services/productService.ts` exports `getBrandsInCategory(category)`; `components/FilterSidebar.tsx` renders any brand not in that set as a plain `<span aria-disabled="true">` with an explanatory `title` instead of a `<Link>`.

**Reasoning**
Hiding brands entirely (option b) would make the sidebar's brand list appear to shrink and grow unpredictably as a shopper changes categories, which is harder to reason about than a stable list where some entries are simply greyed out with a stated reason (*"No Apple products in Automobiles"*).

**Trade-offs**
The brand list stays visually long (all ~43 brands are always present) rather than context-trimmed, in exchange for a predictable, explained list.

**AI Contribution**
Implementing the disabled/enabled branching in the render loop once the underlying rule was specified.

**Human Judgment**
This decision followed directly from a specific instruction to prevent guaranteed-empty combinations proactively rather than reactively — a UX-quality judgment about *where* an error condition should be prevented versus explained after the fact.

## 5. AI-Assisted Development

This section documents categories of work where AI assistance was actually used, based on the available conversation record and the resulting code, and is explicit about what remained the developer's own responsibility in each case.

### 5.1 Implementation of new Next.js/React features
**Problem existed:** Several features (order history, product-linked messaging, a working currency selector, an AI shopping assistant, a search-history dropdown, a mobile navigation drawer) did not previously exist or were decorative/non-functional (the language/currency selector, for instance, existed visually before it did anything).
**How AI assistance was useful:** Generating the first working version of new components/hooks/services following the project's existing conventions (CSS Modules, Context+hook pairs, `services/*.ts` pure functions).
**What the developer still had to understand:** Which existing utility already solved part of the problem (e.g., recognizing that `filterProducts()` and `getTrendingProductIds()` already existed before wiring the AI Assistant's tool or the auth page's "Explore" button to them, rather than re-implementing catalog search).
**What was verified manually:** Every new page/feature was checked against a running `next dev` server, not just read as generated code — see Section 14 for the specific verification methods used per feature.
**Limitations:** Generated code needed project-specific correction more than once — see Section 8 for concrete cases (opacity/legibility, an incorrect assumption about which element was clipping an underline indicator, and a link destination that didn't match the actual intent behind a request).

### 5.2 Debugging and error diagnosis
**Problem existed:** Runtime bugs that were not obvious from reading the code alone — a React Server Component silently receiving broken data, a CSS pseudo-element that never painted despite having entirely correct declared styles, a mock test server truncating responses.
**How AI assistance was useful:** Proposing hypotheses and, critically, proposing *instrumented tests* (direct DOM measurement via Playwright, raw `curl` requests against API routes, direct `getComputedStyle` queries) rather than only proposing code changes on faith.
**What the developer still had to understand:** That a first hypothesis can be wrong — see the thumbnail-underline issue in Section 7, where an initial fix (adjusting the thumbnail *row's* overflow/padding) did not work, and only a second, more targeted investigation (forcibly overriding `overflow: visible` via script and re-screenshotting) revealed the real cause was the thumbnail *button's own* `overflow: hidden`.
**What was verified manually:** Every fix in this project was re-tested after being applied — via `npx tsc --noEmit`, `npm run lint`, `npm run build`, and targeted Playwright scripts — rather than assumed correct once written.
**Limitations:** AI-proposed root causes were sometimes plausible but incorrect on the first attempt (documented explicitly in Section 8, not glossed over).

### 5.3 Responsive UI and CSS layout
**Problem existed:** A mobile header that wrapped across multiple lines and consumed roughly half of a phone screen's height before any page content was visible; an auth page whose image panel used the same cramped treatment on tablets (768–1023px) as on phones, despite tablets having enough width for the desktop-style side-by-side layout.
**How AI assistance was useful:** Proposing breakpoint restructuring and flex-layout rewrites, and in the mobile-header case, correctly diagnosing that CSS `flex-wrap` combined with a desktop-tuned `flex-basis` was still forcing a second line even after unrelated header items had been hidden — confirmed by direct `boundingClientRect` measurement before and after (header height measured at ~392px before the fix, ~65px after, on a 375×812 viewport).
**What the developer still had to understand:** Which breakpoint number was actually appropriate for this specific layout — the auth page's breakpoint was set once, found to be wrong for tablets by the developer, changed, found to still not match the desired stacking order, and changed again to the layout the developer actually wanted (see Section 8, "Explore" button episode, for the closely related iteration).
**What was verified manually:** Screenshots were taken and visually reviewed at multiple concrete viewport sizes (375×812, 390×844, 375×667, 768×1024, 1023×768, 1280×900) rather than relying on a single "looks responsive" check.
**Limitations:** Several rounds of adjustment were required before the layout matched what was actually wanted — responsive CSS changes were not correct on the first attempt in more than one instance.

### 5.4 Accessibility review and correction
**Problem existed:** New interactive elements (a search-suggestions dropdown, a category-thumbnail carousel, a mobile drawer) needed real accessibility behavior (focus management, ARIA relationships, keyboard navigation), not just visual styling.
**How AI assistance was useful:** Applying the project's own established accessibility conventions consistently to new components (roving `tabIndex`, `aria-current`, `aria-controls`/`aria-expanded` pairing, `role="listbox"`/`role="option"` for the search dropdown).
**What the developer still had to understand:** *Why* a given ARIA pattern applies — e.g., that a set of link-like navigation items should use `role="navigation"` semantics rather than `role="menu"`, a distinction `components/CategoryFlyout.tsx`'s own comment makes explicitly (*"not an ARIA 'menu' — role='menu'/'menuitem' implies application-menu keyboard behavior... that a set of navigation links shouldn't opt into"*).
**What was verified manually:** Keyboard interaction (arrow keys, Escape, Tab order) was tested via Playwright's keyboard API against the running app, not assumed from the markup alone.
**Limitations:** At least one real accessibility bug shipped and had to be found after the fact rather than being caught during initial implementation — see Section 7's "thumbnail underline" issue, which is as much an accessibility/visual-affordance bug (the active-selection indicator was invisible) as a CSS bug.

### 5.5 State management and performance-sensitive architecture
**Problem existed:** A streaming AI chat feature updates its message content on every received token; naively storing that in one shared context would re-render every consumer (including the navbar button) on every token.
**How AI assistance was useful:** Applying a context-splitting pattern (`AIAssistantUIContext` for open/close state, `AIAssistantChatContext` for the fast-changing message stream) so only components that actually need per-token updates subscribe to them.

## 7. Debugging and Problem-Solving Journal

### Issue: React Server Component receiving broken data from a `"use client"` module

**Symptom**
Data (`SHIP_COUNTRIES`) exported from a client-marked file resolved incorrectly (effectively empty/broken) when imported into a Server Component.

**Evidence**
A server-rendered page (`app/about/page.tsx`, which reports real computed catalog stats including the number of ship-to countries) produced an incorrect value when reading data from `context/ShipCountryContext.tsx`.

**Investigation**
The import chain was traced: the data was declared inside a file with a `"use client"` directive at the top.

**Likely Cause**
Next.js treats every export of a `"use client"` file as a client-reference proxy for React Server Component serialization purposes — even a plain constant array, not just components. A Server Component importing that export does not get the real value.

**AI Assistance**
Identifying this as a known Next.js RSC-boundary behavior (not a typo or a logic bug) and proposing the fix: extract the plain data into its own file with no `"use client"` directive.

**Developer Judgment**
Confirming the fix actually addressed a *real* framework boundary rule (not coincidentally "fixing" something unrelated) required understanding what `"use client"` does at the module level, not just at the component level.

**Fix**
`context/shipCountriesData.ts` was created as a plain (non-directive) module holding `SHIP_COUNTRIES`; `context/ShipCountryContext.tsx` re-exports it for backward compatibility with existing client-side imports.

**Verification**
The affected server-rendered page was re-checked and confirmed to report the correct count.

**Lesson**
A `"use client"` directive's effect on **every** export of that file — not just components — is a Next.js-specific gotcha that is easy to miss when a data constant happens to live in the same file as a client-only hook/context for convenience.

### Issue: Mock test server truncating streamed responses after the first word

**Symptom**
During local testing of the AI Assistant (using a hand-written mock SSE server to avoid requiring a real API key), the second round of a tool-use conversation streamed only one word before appearing to finish.

The mock server (a local testing utility, not part of the shipped application) was corrected to listen on the response's `close` event.

### Issue: Mobile header wrapping to multiple lines despite hiding unrelated elements

**Symptom**
On a 375px-wide viewport, the site header rendered as a tall, multi-line stack (measured at approximately 392px tall — roughly half the visible screen on a typical phone) instead of a single compact row, even after account links and the secondary navigation row were hidden via CSS media queries.

**Evidence**
Direct `boundingClientRect` measurement via a Playwright script before and after the fix: header height dropped from ~392px to ~65px on a 375×812 viewport.

**Investigation**
Inspecting the computed layout of each header child at the mobile breakpoint to see where the row was actually breaking.

**Likely Cause**
The search input's desktop-tuned flex sizing (`flex: 0.98 1 20rem`, meaning a ~320px flex-basis) was wider than the space remaining after the hamburger button and logo icon on a 375px-wide row, so the browser's flex-wrap algorithm moved it to a new line entirely, taking the AI Assistant button and cart icon down with it.

Proposing a mobile-specific override: `flex-wrap: nowrap` on the header row plus a mobile-specific `flex: 1 1 auto` (no large fixed basis) on the search field, so it fills remaining space instead of trying to claim a desktop-sized minimum.

**Fix**
`Navbar.module.css`'s mobile breakpoint block overrides `.headerRow` to `flex-wrap: nowrap` and `.searchWrap` to `flex: 1 1 auto; max-width: none; margin-left: 0`.

**Verification**
Re-measured via Playwright (single-row layout confirmed, no horizontal overflow at 375px) and visually confirmed via screenshot.

**Lesson**

### Issue: Active-thumbnail underline indicator never actually visible (clipped by its own parent)

**Symptom**
A small blue underline meant to indicate which category thumbnail is currently active/shown on the main image did not appear on screen, despite its CSS declaration being entirely correct.

**Evidence**
`getComputedStyle(element, "::after")` confirmed the pseudo-element had a real, non-transparent background color, `opacity: 1`, correct `position: absolute`, and a correct offset — yet a cropped screenshot of the exact region showed nothing.

**Investigation**
Multiple hypotheses were tested in sequence, not just the first one:
1. First hypothesis: the thumbnail *row's* `overflow-x: auto` was forcing `overflow-y` to also become `auto` (a real, documented CSS interoperability quirk) and clipping the underline. This was implemented as a fix (extra bottom padding, explicit `overflow-y: visible`) — and **did not resolve the problem**, confirmed by re-screenshotting.
2. Second investigation: `overflow` was forced to `visible` directly via a script against the live page, bypassing all CSS — and the underline **still did not appear**, which disproved hypothesis 1 entirely.
3. Re-inspection of the actual `.thumbBtn` rule (the 44×44px button itself, not its row) found `overflow: hidden` — added originally to clip the thumbnail photo to a rounded square — which was *also* clipping the button's own `::after` pseudo-element, since that pseudo-element is deliberately positioned 8px *outside* the button's own box (documented in the button's own pre-existing comment: *"a real gap underneath the button... deliberately, so the indicator doesn't read as touching/cutting into the photo"*).

**Likely Cause**
`overflow: hidden` on `.thumbBtn` clipped its own out-of-bounds `::after` pseudo-element — an existing, structural bug that predated the recent work on this component, not something introduced by it.

**AI Assistance**
Proposing and testing the first hypothesis, then — critically — proposing the disproof test (forcing `overflow: visible` directly) once the first fix demonstrably did not work, rather than declaring the first fix sufficient without re-verifying.

**Developer Judgment**
Explicitly reverting the first (ineffective) fix rather than leaving it in place alongside the real fix, once the true cause was found — keeping the codebase's comments accurate to what actually mattered was treated as part of the fix, not an afterthought.

**Fix**
`overflow: hidden` was removed from `.thumbBtn` and moved to a new, dedicated inner wrapper (`.thumbImageClip`) that clips only the photo, leaving the button's own box free to show its `::after` underline outside its bounds.

**Verification**
A cropped screenshot of the exact thumbnail region, before and after, directly showing the underline's absence and then presence.

**Lesson**
A CSS declaration having entirely correct computed style values does not guarantee it is actually painted — an ancestor's `overflow` can silently clip correct content, and the first plausible ancestor is not necessarily the right one; disproving a wrong hypothesis by direct experiment (not just re-reading the CSS) was what actually found the real cause.

### 8.2 "Explore" button initially linked to a single product page, not the category

**AI/Initial Approach**

**Why the Correction Was Better**
It matches what the button's own label promises (exploring a category, not landing on one item), while still satisfying the underlying "trending" requirement — just applied to what the destination *page* shows, rather than to which single product is picked.

### 8.3 Glassmorphism button hover state lost its own visual effect

**AI/Initial Approach**
The "Explore" button's glass effect was implemented with a semi-transparent blue fill (55% opacity at rest) that became more opaque (70%) on hover, intended to signal interactivity.

**Problem**
At that opacity, especially over a busy/dark photo, the button read as a plain solid-blue pill rather than a translucent glass surface — the hover state made this worse, not better, since it moved *further* from transparent.

**Correction**
The base fill opacity was substantially reduced (to 28%, low enough that the underlying photo visibly shows through), and the hover state was changed to rely primarily on a lift (`translateY`) and a deepened drop shadow for interactive feedback, with only a small opacity increase (to 34%) rather than a large one. **Why the Correction Was Better**
The glass effect is now visually present at rest and preserved on hover, and readability is protected by a targeted technique (text-shadow) rather than by making the background opaque enough to defeat the requested effect.

### 8.4 Verification scripts themselves produced false results from overly broad selectors

**AI/Initial Approach**
Several Playwright verification scripts used broad CSS-Module-hash-agnostic selectors such as `[class*="panel"]` or `[class*="emptyState"]` to check for a specific component's presence.

## 9. Performance Engineering

**Image optimization.** Every product/photo image in the app renders through `next/image` (verified across `ProductCard.tsx`, `ProductGallery.tsx`, `AuthSplitPage.tsx`, `CategoryFlyout.tsx`, `Navbar.tsx`). `ProductCard.tsx` sets explicit `width`/`height` on grid images (avoiding layout shift) and `loading="lazy"` for every card except an opt-in `priority` card (used for the first, above-the-fold item on a page — confirmed in `app/listing/page.tsx`'s `priority={i === 0}`). `AuthSplitPage.tsx`'s full-bleed showcase image uses `fill` with an explicit `sizes="(min-width: 64rem) 50vw, 100vw"` — its own comment states the reasoning directly: *"Without `sizes`, next/image assumes this fills the whole viewport width and requests an image sized for that on every device — several times larger than the ~50vw (mobile: 100vw) this pane actually renders at."* This is a specific, evidenced improvement, not a generic claim.

**Loading behavior / LCP.** The home page and product pages use ISR (`revalidate = 3600` on both `app/page.tsx` and `app/product/[id]/page.tsx`) so the HTML for the initial view is pre-rendered rather than assembled client-side. `app/product/[id]/page.tsx` also calls `generateStaticParams()` so every product page is built ahead of request time. **Not verifiable from the available evidence:** no Lighthouse/Web Vitals report or Core Web Vitals field data exists in the project to cite an actual LCP number.

**Unnecessary re-rendering.** The AI Assistant's context is deliberately split into `AIAssistantUIContext` (open/close — rarely changes) and `AIAssistantChatContext` (message stream — changes on every token), specifically so components that only need open/close state (the navbar trigger button) do not re-render on every streamed token. This is a concrete, code-verified performance decision, not a general claim.

**Client/server boundaries.** `services/productService.ts` and `services/productData.ts` have no `"use client"` directive and no browser-only API usage, so they run identically during server rendering (`app/listing/page.tsx`, `app/product/[id]/page.tsx`) and inside client components (`components/CategoryFlyout.tsx`, `components/Navbar.tsx`'s live search suggestions) without duplicating catalog logic or shipping a second copy of the data model.

**Bundle considerations.** `package.json` shows a deliberately small dependency surface: the only UI-facing runtime dependencies are `next`, `react`, `react-dom`, `lucide-react` (icons), and `react-markdown` (added specifically and only for rendering the AI Assistant's streamed Markdown responses — confirmed as the single new dependency added for that entire feature). No component library, no CSS framework, no state-management library, and no AI provider SDK are present.

**CSS/animations.** `app/globals.css` defines a global `prefers-reduced-motion: reduce` override that forces all animation/transition durations to near-zero and disables smooth scrolling, applied once at the root rather than per-component. Motion elsewhere in the app (thumbnail hover underline, showcase image fade, dialog entrance) uses `transform`/`opacity`-only transitions, which are cheaper for the browser to animate than layout-affecting properties — this is a **reasonable engineering interpretation** based on the properties used, not a claim backed by a measured frame-rate profile.

**Search/filtering cost.** `filterProducts()` runs synchronously over the in-memory 59-product array on every keystroke in the navbar's live search suggestions (`components/Navbar.tsx`). This is inexpensive at the current catalog size; `Navbar.tsx`'s own comment acknowledges the trade-off directly: *"The catalog is small (~60 products)... so matching on every keystroke here is a synchronous in-memory filter, not a network round trip — no debounce needed for it to feel instant."* This would need re-evaluation (debouncing, indexing, or moving to a real search backend) if the catalog grew substantially — an **outstanding consideration**, not a current problem.

**Warnings observed during development.** The available conversation record documents one concrete `next/image` console warning that was diagnosed and fixed: a `fill`-mode image's positioning ancestor was unstyled (`position: static`), which Next.js's own dev-time warning flagged because `fill` was resolving its absolute positioning against a *further* ancestor than the immediate parent, even though the visual result happened to be identical. This was fixed by giving the immediate wrapper `position: relative` explicitly (see `AuthSplitPage.module.css`'s `.imageInner` comment). **No other framework warnings are recorded as still-outstanding** in the available evidence — but this report does not claim the console is warning-free in every possible state, since a full audit of every route/interaction was not exhaustively re-run as part of producing this report.

## 11. UX/UI Decision-Making

**Navigation.** The header progressively discloses controls by viewport width rather than removing functionality outright: the AI Assistant control collapses to icon-only (not hidden) below `56rem` (`AIAssistantButton.module.css`'s own comment: *"Icon-only below the width the label starts crowding the search field and header links... not hidden entirely (the assistant needs to stay easy to find at every width)"*), while account links, the category row, and the deliver-to/language selectors move into a hamburger drawer (`MobileNavDrawer.tsx`) below the same breakpoint — with Cart deliberately kept outside the drawer as a persistent one-tap icon, reasoned in `Navbar.tsx`'s own comment as matching common mobile e-commerce convention.

**Product cards.** Distinguish three real, non-decorative signals: a discount badge (only when `oldPrice` is genuinely set), a "Deal" badge as a fallback for `hot`-flagged-but-not-discounted items (closing a gap where such items previously showed no badge despite matching the Deals filter), and a "Trending" badge driven by the same `getTrendingProductIds()` ranking used elsewhere, passed in explicitly per-listing rather than computed redundantly per card.

**Product detail page.** Brand information exists on every product (`Product.brand`) but, before recent work, was only ever emitted into invisible JSON-LD structured data — never shown to a visitor, and never filterable. This was identified as a real gap (a shopper could not see or search by brand despite the search placeholder promising it) and corrected by adding a visible "Brand: X" line linking to a real brand filter, plus a full Brand section in `FilterSidebar.tsx`.

**Listing/filter experience.** Filter state lives entirely in the URL (`app/listing/page.tsx`'s `searchParams`), which means every filter combination is bookmarkable, shareable, and works without client-side JavaScript. A specific UX failure mode was identified and fixed: combining a leftover search term with a newly-picked, unrelated filter (category, brand, etc.) could produce a guaranteed zero-result page. Rather than only showing an empty state, the listing page now falls back to dropping the search term (keeping the other filter) when that combination would otherwise be empty, with a clearly-worded, visibly red notice explaining what happened — a deliberate choice to explain an unexpected result rather than silently substitute one.

**Authentication pages.** `AuthSplitPage.tsx` is a dedicated full-page sign-in/sign-up experience (distinct from the existing contextual `AuthModal`, which remains unchanged for in-flow prompts like "sign in to add to wishlist"). Layout breakpoints were iterated more than once based on direct feedback: an initial `64rem` (desktop-only) breakpoint for the side-by-side layout left tablets (768–1023px) using the same compact, phone-oriented single-column treatment despite having ample width for the two-column layout; this was corrected, then further clarified (per explicit feedback) that the *stacked* order — info, then image, then thumbnails — was actually the desired arrangement for phones and tablets, with only the desktop breakpoint keeping the side-by-side layout. The showcase image's height was likewise iterated based on direct measurement and feedback until it reached an explicitly requested 400px floor, with a separate, smaller floor preserved specifically for short viewports so the primary form action (Sign In / Create Account) never gets pushed below the fold.

**Loading/feedback/error states.** The AI Assistant implements a distinct "thinking" indicator (three animated dots) shown only before the first streamed token arrives, a "Jump to latest" affordance that appears only once a user has scrolled away from the bottom during streaming, and explicit, human-readable error messages for a missing API key or an upstream failure — verified directly in `components/AIAssistantPanel.tsx` and `app/api/assistant/route.ts`.

**Search discoverability.** A recent-searches dropdown (`SearchHistoryDropdown.tsx`) was added below the navbar search field, showing both past search terms (removable individually or all at once) and live-matching real products as the user types — falling back to real products from the user's *most recent matching* past search (not just the single latest term, which could itself have zero catalog matches) when the field is empty but has been used before.

## 12. Security and Secrets

**Variable names used (values never reproduced here).** The AI Assistant feature reads exactly one secret-bearing variable, `OPENROUTER_API_KEY`, and one optional non-secret configuration variable, `OPENROUTER_MODEL`. Both are read **only** inside `app/api/assistant/route.ts` (a server-only Route Handler) — `lib/ai.ts`, which is imported by that route, never references `process.env.OPENROUTER_API_KEY` at all (verified by direct inspection of the file). Neither variable is prefixed `NEXT_PUBLIC_`, which means Next.js never bundles it into client-side JavaScript in the first place — this is a framework-level guarantee, not just a convention being followed.

**No paid-API fallback.** As documented in Section 4, `lib/ai.ts`'s `isFreeModelId()` guard is checked on every request in `route.ts` before any upstream call is made, and the app refuses to proceed (with a clear, non-sensitive error message) rather than silently falling back to a different, potentially paid model.

**Error messages do not leak secrets.** `route.ts`'s error responses use fixed, generic strings (e.g., *"The AI assistant isn't configured yet (missing server API key)."*) rather than including any part of the actual environment value, upstream response body, or stack trace.

**Authentication-adjacent security judgment.** As documented in Section 4, `useAuthForm.ts` deliberately returns the same generic error for "no such account" and "wrong password," specifically to avoid letting a failed sign-in attempt be used to enumerate which emails have accounts — a real security-relevant UX decision, applied to a system that is otherwise explicitly a local-only prototype with no real backend.

**What this project does not claim.** This is a frontend-only prototype with no real backend, no encrypted credential storage, and no server-side session mechanism — `AuthContext.tsx` and `useAuthForm.ts` both state this directly in their own comments, and the UI itself displays a "Prototype" notice on the auth pages. This report does not claim the application is production-secure; it claims that the specific secret it does handle (the OpenRouter key) is handled correctly for a Next.js app of this kind.

## 15. Significant Features

### Feature: Server-rendered, URL-driven product listing and filtering

- **Purpose:** Let a shopper filter, sort, search, and paginate the catalog with bookmarkable/shareable URLs and no JavaScript dependency for the core browsing experience.
- **Implementation:** `app/listing/page.tsx` (Server Component) parses and validates `searchParams` into a typed `ListingFilters` object, then calls `filterProducts()` and `paginate()` from `services/productService.ts`.
- **Important files:** `app/listing/page.tsx`, `services/productService.ts`, `components/FilterSidebar.tsx`, `components/ActiveFilterChips.tsx`, `components/Pagination.tsx`.
- **State/data flow:** URL search params → `parseFilters()` → `filterProducts()`/`paginate()` → server-rendered HTML. No client-side filter state exists at all for the primary experience.
- **AI assistance:** Implementing the filter-parsing/validation logic and the shared URL-building helpers (`buildFilterHref`/`buildPageHref`) that every filter control (sidebar, chips, sort form, pagination) goes through, avoiding query-param-name drift across controls.
- **Developer decisions:** Choosing to keep this server-rendered rather than client-filtered; deciding how a malformed or invalid query param should fail safely (e.g., `Number("garbage")` is `NaN`, which is neither `null` nor `undefined` — a naive `!= null` check would let it silently zero out every result via `price >= NaN`; `toFiniteNumber()` exists specifically to guard against this, per the file's own comment).
- **Problems encountered:** The search+filter zero-result dead end (Section 4); the whole-string vs. token-based search matching bug (Section 4).
- **Improvements:** Brand filtering added, with category-aware disabling of brands that don't apply (Section 4); token-based multi-word search matching.
- **Verification:** Confirmed via direct browser testing of multiple real filter/search/brand combinations, including the specific fallback and disabled-brand behaviors.
- **Current limitations:** No fuzzy/typo-tolerant search; search cost scales linearly with catalog size (acceptable at 59 products, flagged as a future consideration in Section 9).

### Feature: AI Shopping Assistant (streaming chat, tool-augmented)

- **Purpose:** A conversational assistant that recommends real catalog products based on budget/use-case, not a generic chatbot.
- **Implementation:** `app/api/assistant/route.ts` (server-only streaming Route Handler) proxies to OpenRouter's OpenAI-compatible chat-completions API, parsing SSE chunks and re-emitting a smaller, custom SSE protocol to the browser; `context/AIAssistantContext.tsx` consumes that stream client-side; `components/AIAssistantPanel.tsx` renders it (Markdown via `react-markdown`, product cards, thinking indicator, Stop button, auto-scroll).
- **Important files:** `lib/ai.ts`, `app/api/assistant/route.ts`, `context/AIAssistantContext.tsx`, `components/AIAssistantPanel.tsx`, `components/AIAssistantButton.tsx`.
- **State/data flow:** User message → `fetch("/api/assistant")` → server builds/streams an OpenRouter chat-completions request (with the `search_products` tool available) → on `tool_calls`, the server executes `executeSearchProducts()` (a thin wrapper around the real `filterProducts()`) and re-prompts the model with the real results → text and product-result events stream back to the browser as they arrive.
- **AI assistance:** Implementing the SSE parsing/tool-use loop, the streaming UI (thinking indicator, auto-scroll-with-"stay if scrolled up" logic, Stop-button cancellation via `AbortController` threaded through to the upstream `fetch`), and the provider migration from Anthropic to OpenRouter.
- **Developer decisions:** No AI SDK dependency (Section 4); the free-model guard as a hard runtime invariant (Section 4); the context-splitting performance pattern (Section 9).
- **Problems encountered:** The mock-server truncation bug (Section 7); ensuring cancellation is real (server-side, not just UI) rather than cosmetic.
- **Improvements:** Migrated the entire provider integration from a direct Anthropic API call to OpenRouter's free tier without changing the client-facing wire protocol at all, so no changes were needed in `AIAssistantContext.tsx` or `AIAssistantPanel.tsx`.
- **Verification:** SSE parsing and the tool-use loop were exercised end-to-end against a mock server standing in for the real API (confirmed real product data flowing through the real `filterProducts()`); Stop-button cancellation was verified to leave partial text intact and allow an immediate new message.
- **Current limitations:** Not tested against a live OpenRouter key in the available development environment (Section 14); response quality/behavior can vary since `openrouter/free` selects among multiple underlying free models rather than one fixed model (an explicit, disclosed trade-off, Section 4).

### Feature: Real order history (Checkout → Profile)

- **Implementation:** `services/orderService.ts` (localStorage, scoped per signed-in user's email); `app/checkout/page.tsx` calls `saveOrder()` on successful checkout and displays a generated order number; `app/profile/page.tsx` reads `getOrders()` for a "My orders" view and an "Orders placed" stat.

- **Problems encountered:** Not verifiable from the available evidence beyond the guest-checkout scoping decision itself.

## 17. AI Development Workflow

The workflow actually used, based on the available conversation record, followed this shape:

```
Requirement (often stated informally, as a user-facing problem)
        ↓
Problem definition — restating the actual, specific technical problem
        ↓
Inspect existing code — locating relevant existing files/utilities BEFORE writing anything new
        ↓
Prompt AI for an implementation, scoped to the existing conventions found above
        ↓
AI proposes/writes a solution
        ↓
Evaluate the proposal against the actual requirement and the existing codebase
        ↓
Implement/integrate into the real files
        ↓
Run the application (next dev) and exercise the actual feature
        ↓
Run automated checks (tsc --noEmit, eslint, and/or a targeted Playwright script)
        ↓
Inspect errors/warnings/actual rendered output — not just "does it compile"
        ↓
Identify weaknesses (a wrong assumption, an incomplete fix, a UX problem)
        ↓
Ask for refinement, or correct the implementation directly
        ↓
Retest (rerun the same verification steps)
        ↓
Final verification — including a full production build before considering a change set complete
```

**Why this differs from copying AI-generated code directly.** Several concrete points in this report are direct evidence that this workflow was actually followed rather than skipped:

1. **"Inspect existing code" was a real, repeated step**, not a formality — multiple features (the AI Assistant's product tool, the auth page's "Explore" button, the search dropdown's product suggestions) were explicitly built by locating and reusing an *already-existing* utility (`filterProducts()`, `getCategoryPreview()`, `getTrendingProductIds()`) rather than generating a second, parallel implementation.
2. **Proposed fixes were sometimes wrong, and were caught by testing, not assumed correct** — Section 8 documents four concrete cases where a first implementation was tested, found insufficient, and corrected.
3. **"Run the application" and "run automated checks" were not skipped** — the specific commands (`npx tsc --noEmit`, `npm run lint`, `npm run build`) and their pass/fail results are referenced throughout the available conversation record as a standard step after each change, not an occasional afterthought.
4. **Verification scripts were themselves debugged when they gave misleading results** (Section 8.4) — evidence that test output was treated as something to verify, not as ground truth by default.

## 18. Evidence of Developer Judgment

- **Rejecting an unsuitable implementation pattern for a new requirement.** The native `<dialog>` modal pattern, used successfully three times elsewhere in the app, was deliberately *not* reused for the AI Assistant panel because that panel needed the background to remain interactive — a requirement a true modal dialog cannot satisfy. (Section 4)
- **Choosing between two working approaches based on an operational constraint, not just correctness.** Choosing OpenRouter's `openrouter/free` router over pinning one specific free model, specifically because the free-model landscape is known to change over time. (Section 4)
- **Deciding a warning/bug was real and worth fixing versus cosmetic.** The `backdrop-filter` build-pipeline issue produced no visible error — only a silently absent visual effect. Treating that as a real defect requiring root-cause investigation (rather than dismissing it as a minor visual nit) is a judgment call. (Section 7)
- **Rejecting a first, plausible root-cause hypothesis after it failed to fix the problem.** The thumbnail-underline investigation explicitly disproved its own first hypothesis via a targeted experiment before accepting a different one. (Section 7/8.1)
- **Protecting a stated business constraint by encoding it as a runtime invariant, not just following it once.** The "never call a paid model" requirement was implemented as a guard checked on every request, not just a default configuration value that could silently drift. (Section 4/12)
- **Validating generated code against the actual, current dependency set rather than trusting a suggestion.** Confirming via `package.json` that no AI provider SDK was actually added, keeping the dependency footprint to exactly what was stated as acceptable.
- **Deciding what belongs in a client vs. server component, and catching when that boundary was violated by the framework's own behavior.** The RSC "use client" export-proxy issue (Section 7) required understanding a specific Next.js framework rule, not just moving code around until an error disappeared.
- **Testing behavior instead of trusting a tool's output.** The false-positive/false-negative test-selector issue (Section 8.4) was only caught by manually cross-checking a test result against the actual rendered HTML.
- **Providing user-facing honesty about a system's real limitations rather than a more impressive-sounding but false claim.** The guest-checkout order-persistence messaging (Section 15), the "Prototype" notice on the auth pages, and this report's own explicit "not verifiable" labeling are all instances of the same underlying discipline.

## 19. What I Learned

- **A framework's rendering-model rules can silently corrupt data, not just throw an error.** The `"use client"`-export-proxy behavior only became findable once the *rule itself* (that the directive affects every export of a file, not just components) was understood — the symptom alone (a wrong value on the server) didn't point directly at the cause.
- **A CSS declaration with entirely correct computed style values is not proof it is actually rendering.** The thumbnail-underline bug is a direct lesson that `getComputedStyle` confirming "the styles are right" is a necessary check, not a sufficient one — an ancestor's `overflow` can still make correct styles invisible, and finding the *right* ancestor sometimes requires disproving a wrong guess first.
- **Build tooling is part of the system to debug, not just the code.** The Turbopack/Lightning CSS `backdrop-filter` issue would not have been found by re-reading CSS syntax repeatedly; it required testing the property in isolation and considering the compiler itself as a suspect.
- **Responsive design bugs often live in a sibling's leftover sizing rule, not the element that was actually changed.** Hiding header elements at a breakpoint did not, by itself, fix the header's height — the search field's own desktop-tuned `flex-basis` was the real remaining cause, only found by inspecting computed geometry directly.
- **Security-relevant decisions are often about what NOT to reveal.** The generic "invalid email or password" message and the "never fall back to a paid model, ever, silently" guard are both examples where the *safe* behavior required deliberately not doing the more convenient thing.
- **Requirements communicated informally still need to be interpreted precisely, and that interpretation can be wrong.** The "Explore" button's destination (a product vs. a category page) is direct evidence that a reasonable reading of an ambiguous instruction can still not match what was actually meant — and that the fix is to ask/clarify and re-implement, not to defend the first interpretation.
- **Verification tooling needs its own verification.** Writing a Playwright script is not the end of testing — a test that passes or fails for the wrong reason (an overly broad selector matching an unrelated, globally-mounted element) is worse than no test, because it creates false confidence.
- **A `localStorage`-plus-`useEffect` hydration pattern is a recurring, learnable solution to a specific, recurring problem** (SSR/CSR state mismatch) — recognizing the pattern once made every subsequent instance of the same problem (Cart, Wishlist, Auth, search history) faster and more consistent to solve correctly.
- **AI assistance is fastest and most reliable when it is pointed at the actual, existing code first.** Every feature in this project that reused an existing utility function instead of duplicating catalog logic did so because the existing code was located and read *before* asking for an implementation — not because the AI tool did that automatically without being directed to.
- **AI-proposed fixes are a starting hypothesis, not a guaranteed answer** — several real, documented cases in this project required a second (or third) attempt after the first fix demonstrably did not work when actually tested.

## 20. Final Engineering Assessment

### What is strong
- A consistent, well-documented architectural pattern (Context + hook + service layer, with `services/*.ts` kept framework-agnostic) applied uniformly across cart, wishlist, auth, currency, and search-history features.
- A real, working streaming AI feature built without an AI SDK dependency, with genuine server-side cancellation and a hard, code-enforced guard against incurring API cost.
- Accessibility conventions (skip link, focus-visible ring, 44px targets, `prefers-reduced-motion`, semantic real interactive elements) defined once, globally, and reused consistently rather than reinvented per component.
- A server-rendered, URL-driven listing/filter system that works without client-side JavaScript for its core function.
- A documented, evidence-based debugging history showing that non-trivial bugs (RSC export proxying, a build-tool CSS quirk, a clipped pseudo-element) were actually root-caused rather than patched around.

### What was improved
- Product search went from a whole-string substring check to a token-based match, fixing a real, demonstrable false-negative case.
- The mobile header went from consuming roughly half a phone screen's height to a single, compact row.
- The auth pages' tablet experience went from reusing a phone-oriented compact layout to a layout that actually uses the available width, based on direct feedback and re-testing.
- A structural accessibility/affordance bug (the invisible active-thumbnail indicator) was found and fixed, along with a full explanation of why the first attempted fix did not work.
- The AI Assistant's cost model went from "requires a paid Anthropic key" to "never calls anything but a free tier, enforced at runtime."

### What remains imperfect
- There is no formal, automated regression test suite — verification during development relied on manual/ad hoc scripts and the standard `tsc`/`eslint`/`build` triad, not a CI-enforced suite.
- No accessibility audit tool or screen-reader pass has been performed; accessibility claims are grounded in code-level technique inspection and behavioral (keyboard/DOM) testing, not a scored audit.
- The AI Assistant has not been exercised against a real, live OpenRouter key in the available development environment — only against a faithful mock and against OpenRouter's real, public model-catalog metadata.
- Authentication, orders, messaging, and search history are all `localStorage`-only, with no real backend, account security, or cross-device sync — clearly and repeatedly disclosed in the UI itself, but a real limitation nonetheless.

### What should be improved next
- Add a formal automated test suite (even a small one covering the listing-filter logic and the auth-form validation rules, both pure and easy to unit-test) rather than relying entirely on manual verification.
- Run a real accessibility audit tool and a manual screen-reader pass, and address whatever it surfaces.
- Verify the AI Assistant end-to-end against a real OpenRouter key before considering that feature production-ready.
- Consider what a real backend (accounts, orders, messaging) would require if this project moved beyond a frontend prototype.

### What AI contributed
Implementation speed on well-specified, conventional problems; systematic application of an established pattern across many files; diagnostic hypotheses and instrumented tests for debugging; and drafting documentation (including this report) from a specification and a codebase inspection pass.

### What required developer judgment
Every decision about *which* approach to take when more than one was reasonable; recognizing when a first fix was wrong and needed a second investigation; setting and enforcing hard constraints (cost, security, honesty about prototype status) as code, not just intentions; interpreting informally-stated requirements and correcting course when that interpretation turned out to be wrong; and reviewing, running, and re-testing every change against the real, running application before considering it complete.

## 21. Capstone Summary

This project demonstrates **AI-assisted software engineering, not AI replacing the developer.** Across the available evidence — the current state of the codebase and the recorded development conversation — AI assistance was used to accelerate exploration of the existing code, implementation of new features within established conventions, diagnosis of real bugs, refinement of UI/UX details across multiple iterative rounds, and drafting of this documentation itself.

At every one of those stages, responsibility remained with the developer:

- **Requirements** were stated by the developer, often informally, and had to be interpreted — sometimes incorrectly at first, requiring a corrected re-implementation once feedback clarified the actual intent (Section 8.2).
- **Technical decisions** — which pattern to reuse, which dependency (or lack of one) to accept, which breakpoint or opacity value actually looked right — were made and re-made by the developer based on direct inspection and testing, not accepted on first suggestion.
- **Evaluation** of AI-proposed fixes was not automatic: multiple documented cases (Section 8) show a first attempt being tested, found insufficient, and replaced with a second, better-targeted fix.
- **Testing** was treated as a required step with real commands and real output (`tsc`, `eslint`, `build`, and targeted browser automation) — and the tests themselves were checked for correctness, not just trusted (Section 8.4).
- **Security** decisions (server-only secret handling, a hard no-paid-fallback guard, an enumeration-resistant auth error message) were set as explicit constraints and verified in code, not left implicit.
- **Accessibility** techniques were applied consistently and, where a real gap was found (the clipped underline indicator), fixed and re-verified rather than left as a known issue.
- **UX** decisions — what a button's label should promise and where it should actually lead, what a mobile header should prioritize, how a zero-result filter combination should be explained rather than silently returned — were made and refined based on direct, iterative human feedback.
- **Final implementation** was only considered complete once it passed the developer's own verification steps against the real, running application — not once AI-generated code compiled.

This report itself follows the same discipline it describes: every claim in it is either backed by a specific file or command output that can be independently re-checked against this repository, or is explicitly labeled as an interpretation or as not verifiable from the available evidence.
